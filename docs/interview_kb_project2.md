# 面试知识库文档｜项目二：跨境电商 NL2SQL 智能问数与经营异常排查 Agent (`ecom-nl2sql-anomaly-agent`)

> **文档用途**：供面试问答 Agent 知识库检索使用。所有架构设计、仿真数仓规模、实测 EX 准确率、串并行耗时与 V1 翻车 SQL 均来自本人真实代码与回归评测，**严禁编造虚假企业线上数据**。

## 一、项目基本信息与真实定位

- **项目名称**：跨境电商 NL2SQL 智能问数与经营异常排查 Agent（`ecom-nl2sql-anomaly-agent`）
- **项目属性**：与项目一（宠物跨境电商评论问答）处于**同一垂直业务域**的个人开源工程项目，补齐跨境电商“非结构化评论 RAG + 结构化经营数仓 NL2SQL & 异常排查”双闭环能力。
- **技术栈**：Python 3.12、`FastAPI`、`LangGraph`、`sqlglot`（AST 解析）、`PostgreSQL 16`（独立 `ecom_bi` Schema，90 天 10,174 订单 + 1,080 广告日汇总）、`YAML 语义层`、`ThreadPoolExecutor`、`Langfuse v2`、`DeepSeek`、`pytest`
- **一句话电梯演讲（30 秒版）**：
  > 跨境电商运营看经营报表时，常把指标问数、口径核对和异常排查混在一句话里，而普通裸 NL2SQL 极易算错口径、写多对多 JOIN 导致金额膨胀，或者把 ETL 断数误判为业务暴跌。我基于结构化语义层、`sqlglot` AST 只读安全护栏、LangGraph 报错/空结果自修复循环和三路并发异常排查引擎搭了这套系统：在 16 题黄金评测集上，把 NL2SQL 执行准确率（EX）从 50% 提升到 100%，三路异常排查数据库耗时通过并行从 29.8ms 降到 12.0ms（-59.7%），4 类注入异常（品控退单、管道断数、广告 ACOS 恶化、ETL 重复导入）根因命中率 100%，危险写操作 100% 拦截。

## 二、业务应用场景与核心痛点

### 1. 真实使用场景
面向跨境电商店铺运营、商品经理与数据分析师的每日早会复盘与异常止损：
1. **精准问数（NL2SQL）**：快速查某站点/某 SKU/某大促区间的净营收、退货率、取消率、AOV、ACOS、TACOS，并返回**可复核的只读 SQL 与明细表**。
2. **指标口径百科（Metric QA）**：快速确认公司统一口径（如 GMV vs 净营收、ACOS vs TACOS、退货率分母是否含未发货取消单），未收录指标明确拒答。
3. **经营异常根因排查（Anomaly Investigation）**：当某 SKU 净营收突然暴跌或某站点 GMV 突然翻倍时，系统同时从“营收与广告”“取消与退货”“数据质量（断数/重复导入）”三路并行排查，**先排除数据管道故障，再定位真实业务根因**，避免运营拿着假数据去调广告价或停售商品。

### 2. 仿真数仓中精准构造的 4 类真实企业异常场景（90 天 · 10,174 订单）
1. **场景 A（2026-09-14~16 · `PET-FOUNTAIN-PRO`）**：真实业务波动——水泵噪音品控批次问题导致退取消率飙升（退货率 37.08%，异常单占比 >42%），净营收暴跌；数据管道正常。
2. **场景 B（2026-09-19~20 · `PET-FEEDER-CAM`）**：疑似数据管道断数——订单表连续 2 天 0 行缺失，但广告表 `fact_ads_daily` 曝光与点击完全正常，跨表交叉核验识破“假性营收暴跌”。
3. **场景 C（2026-09-22~24 · `PET-LITTER-AUTO`）**：真实业务波动——广告曝光腰斩、ACOS 恶化至 `64.5%`，订单量同步下滑，退单率与数据质量均正常。
4. **场景 D（2026-09-26 · US 站点）**：数据质量异常——ETL 重复导入导致大量 `order_id` 重复、未去重 GMV 虚高翻倍。

## 三、核心技术难题、踩坑与 V1 vs V2 实测对比

### 1. 为什么必须引入“语义层（Semantic Layer）”？（4 个真实 V1 翻车 Case）
在 8 道 NL2SQL 黄金题评测中，V1（裸表结构）执行准确率仅 **50.0%（4/8）**，V2（语义层）达到 **100.0%（8/8，+50.0 pp）**，V1 暴露了 3 类极典型的真实企业痛点：
- **Case 1：多表粒度不同直接 JOIN 导致指标膨胀（`BI03` · TACOS）**
  - `fact_orders` 是订单明细粒度，`fact_ads_daily` 是“天×站点×SKU”汇总粒度。V1 直接把两表 `JOIN` 在一起 `SUM(ad_spend_usd)`，导致同一天广告费被多笔订单重复累加几十倍，且错用 `s.title` 过滤导致空集；V2 受语义层避坑约束，先用两个子查询/CTE 分别按 `(biz_date, sku_id)` 聚合再 JOIN，精准算出 `10.03%`。
- **Case 2：SQL 语法完全正确，但业务口径算错（`BI04` · AOV & `BI02` · 退货率）**
  - `BI04` 算客单价 AOV 时，V1 除以 `SUM(qty)` 算成了单件均价（`$284.24`），而业务标准口径是每笔已完成订单均价 `COUNT(*)`（正确 **`$308.32`**）；
  - `BI02` 算退货率时，V1 用 `SUM(refund_amount_usd)/SUM(gross_amount_usd)` 算金额占比，而业务标准口径是已发货订单中的退货单数占比（正确 **`37.08%`**）。
- **Case 3：实体字段混淆导致空结果（`BI02` / `BI03` / `BI05`）**
  - 裸 Schema 下，模型多次把 `PET-FOUNTAIN-PRO`、`PET-LITTER-AUTO` 放进 `dim_sku.title = '...'` 而非 `sku_id = '...'`，SQL 不报错但返回 0 行/全 NULL。V2 语义层明确字段示例值，且状态机具备**空结果检测（含 1 行全 NULL 检测）+ 最多 2 次自修复回查机制**。

### 2. 如何保证 NL2SQL 绝对不会删库、拖垮数据库或越权查表？
做了**三层纵深防御**：
1. **意图层前置拦截**：路由节点先拦截写操作与敏感请求（0 触库、1ms 返回）。
2. **`sqlglot` AST 语法树硬校验（`sql_guard.py`）**：
   - 仅允许单条 `SELECT / UNION` 语句，拒绝分号多语句注入；
   - 深度遍历整棵 AST 禁止一切写/DDL 节点（连 `WITH d AS (DELETE ... RETURNING *) SELECT * FROM d` 这类隐蔽 CTE 写操作也会被拦截）；
   - 提取所有真实物理表（剔除 CTE 别名），严格校验在 `ecom_bi` 4 张白名单表内，阻止查询 `pg_shadow` 或跨 Schema 读其他业务表；
   - 禁用 `pg_sleep`、`pg_read_file`、`dblink` 等高危函数；
   - 自动追加或收紧 `LIMIT 200`。
3. **PostgreSQL 数据库事务级兜底**：每次执行显式开启 `SET LOCAL default_transaction_read_only = ON` 与 `SET LOCAL statement_timeout = '3000ms'`。

### 3. 三路并发异常排查的工程价值
- 经营异常排查的 3 个维度（营收与广告、取消与退货、数据质量断数/重复）互相独立，用 `ThreadPoolExecutor(max_workers=3)` 并行查询后，三路数据库平均耗时从串行 **`29.8 ms`** 降至并行 **`12.0 ms`（降延 59.7%）**；同时把单分支耗时和汇总耗时结构化暴露给前端和 Langfuse，便于定位性能瓶颈是在 SQL 查询还是 LLM 总结。
- 归因逻辑坚持**“先排数据质量，再定业务根因”**的确定性规则分级（高/中/低置信度），大模型只负责基于已核验的结构化统计证据撰写可读报告，杜绝“让大模型对着裸明细猜原因”的幻觉问题。

## 四、高频面试追问标准应答库

**Q1：NL2SQL 评测为什么不用字符串相似度，而用 Execution Accuracy (EX)？**
> 答：同一个业务问题可以写出很多条写法完全不同但逻辑等价的 SQL（比如 CTE vs 子查询、别名不同、JOIN 顺序不同），用字符串匹配会严重误判。所以我参照 `IBM/text2sql-eval-toolkit` 的思路，用黄金 SQL 和模型生成的 SQL 都在真实 PostgreSQL 数仓上执行，对比返回行数和数值集合（带容差），衡量真正的执行准确率（EX），同时拆出 `BI04` 这类“SQL 跑通了但口径算错”的隐蔽错误。

**Q2：你项目里的“空结果回查”是怎么做的？有什么细节坑？**
> 答：聚合 SQL（比如 `SELECT SUM(...) WHERE ...`）在条件写错时并不会返回 0 行，而是返回 **1 行且所有列都是 `NULL`**！如果只判断 `len(rows) == 0` 会漏掉这种假成功。所以我在 `SafeSQLExecutor` 里专门写了 `len(rows) == 0 or (len(rows) == 1 and all(v is None for v in rows[0].values()))`，一旦命中就把上次 SQL 和“空集/全 NULL”诊断反馈回 LangGraph 的生成节点，在最多 2 次预算内自我修复，并把每次尝试记录下来供人工核查。

**Q3：为什么异常排查不是全交给 LLM 写 SQL，而是用确定性三路分支 + 规则归因 + LLM 总结？**
> 答：这是产业级 Agent 很重要的“确定性与灵活性分工”原则。日常开放式问数千变万化，适合用语义层 + NL2SQL 保持灵活性；但经营异常排查有非常固定的资深分析师 SOP（必须先查日历断数和订单重复、再看退单率、再看广告曝光与 ACOS），把这三路固化成并行只读工具和确定性归因分级器，不仅速度更快（并行降延 59.7%），而且能保证 4 类高危异常 100% 稳定命中、绝不漏查数据质量问题，最后再交给 LLM 组织清晰的业务结论和止损建议。

**Q4：V2 相比 V1 输入 Token 增加了（6694 → 18626），上线后怎么控制语义层膨胀带来的 Token 成本？**
> 答：非常好的问题。目前数仓只有 4 张表、8 个核心指标，全量注入语义层约增加 700 tokens/次，换来了 EX 从 50% 翻倍到 100% 的巨大收益。如果企业数仓扩展到几百张表、上千个指标，我会把语义层做**动态按需召回（Schema Linking / Metric RAG）**：先根据用户问题用向量+关键词召回最相关的 Top-5 表和指标定义，再动态拼装进 Prompt，并配合 Prompt Prefix Caching（DeepSeek 支持前缀缓存降价）把输入成本压下来。
